## 1) P0 — Sécurité de la stack installée

### 1.1 `privileged: true` sur Home Assistant et Zigbee2MQTT — ✅ TRAITÉ (2026-07-03)
> `privileged` retiré des deux services. Analyse : les deux images tournent en
> root, donc le mapping `devices:` suffit (pas même besoin de `group_add:
> dialout`, qui ne servirait qu'à un conteneur non-root). `docker compose
> config` validé. Point de vigilance résiduel documenté : si un jour Bluetooth
> est utilisé dans HA, il faudra monter `/run/dbus` (pas re-privilégier).
- Où : `docker-compose.yml:30` (homeassistant, cumulé avec `network_mode: host`) et `docker-compose.yml:111` (zigbee2mqtt).
- Risque : une compromission du conteneur HA (intégration tierce, HACS, faille HA)
  donne un root complet sur l'hôte. `privileged` n'est pas nécessaire : le dongle
  Zigbee est déjà passé via `devices:`.
- Correction : retirer `privileged: true` des deux services.
  - **Mode Zigbee2MQTT (setup du mainteneur)** : HA n'a besoin d'AUCUN accès au
    dongle — le mapping `${HOMEASSISTANT_ZIGBEE_DEVICE:-/dev/null}` vaut déjà
    `/dev/null` dans ce mode. Ne pas ajouter de `group_add` à HA dans ce cas.
    Seul le conteneur zigbee2mqtt a besoin du device (`devices:` déjà présent)
    + `group_add: ["dialout"]`.
  - **Mode ZHA** : c'est HA qui a besoin du device (déjà mappé via
    `HOMEASSISTANT_ZIGBEE_DEVICE`) + `group_add: ["dialout"]` sur HA.
  - `/run/udev:ro` déjà monté des deux côtés, suffisant. Tester les deux modes
    après changement (le dongle doit répondre après recreate).

### 1.2 Mosquitto sans authentification — ✅ TRAITÉ (2026-07-03)
> Implémenté selon le plan de migration ci-dessous, intégralement :
> - Install neuve : auth activée par défaut (user `ha`, mot de passe généré,
>   persisté dans `.env` via MQTT_AUTH/MQTT_USER/MQTT_PASSWORD), msgbox avec
>   les identifiants à reporter dans l'intégration MQTT de HA.
> - Stack héritée sans auth : `prompt_mqtt_auth` (zigbee.sh), question
>   explicite avec avertissement HA, défaut **non**. Vérifié par test bats.
> - Auth déjà active + creds connus : idempotent (testé, double passage sans
>   doublon) ; creds perdus : saisie du mot de passe actuel (réappliqué par
>   réécriture du hash) ou régénération.
> - Rotation explicite : menu `status` > "mqtt" (affiche + régénère + restart
>   des conteneurs + msgbox HA). Jamais de rotation silencieuse.
> - passwd Mosquitto généré via `docker run --entrypoint mosquitto_passwd
>   eclipse-mosquitto:2` (args en tableau, pas d'interpolation shell),
>   écriture atomique passwd.new→passwd, chown 1883 + chmod 600.
> - Creds Z2M injectés par upsert awk du bloc `mqtt:` (préserve server,
>   base_topic…), échappement YAML single-quote.
> - Conf mosquitto sans marqueur "Managed by armbian-ha-kit" : jamais touchée.
> Validé E2E : broker réel eclipse-mosquitto:2 avec la conf générée —
> anonyme rejeté, identifiants corrects acceptés, mauvais mot de passe rejeté.
- Où : `scripts/lib/zigbee.sh:279-287` (`allow_anonymous true`, listener `0.0.0.0`).
- Risque : tout processus local ou conteneur du réseau `ha-network` peut publier
  sur MQTT → contrôle des équipements Zigbee (serrures, alarmes…) sans auth.
- Correction : générer un user/password (`mosquitto_passwd`), écrire
  `password_file` dans `mosquitto.conf`, propager les credentials dans la config
  Z2M (`mqtt.user`/`mqtt.password`) et dans l'intégration MQTT de HA.
  S'inspirer du pattern existant de génération du mot de passe Postgres
  (`scripts/install.sh:216`).
- ⚠ **MIGRATION — seul correctif de l'audit cassant pour une stack existante** :
  l'intégration MQTT côté HA n'est PAS gérée par le kit (config UI, stockée dans
  `/config/.storage/core.config_entries`, sans mot de passe). Activer l'auth
  brutalement = HA rejeté par Mosquitto = tous les équipements Zigbee (Z2M)
  indisponibles jusqu'à mise à jour manuelle des identifiants dans HA.
  Implémentation requise :
  1. Install neuve : auth activée par défaut, credentials affichés dans le
     résumé final (à reporter dans l'intégration MQTT de HA).
  2. Mise à jour : détecter un `mosquitto.conf` existant sans `password_file`
     → question wizard explicite avec avertissement, défaut = **non**.
     Si accepté : migrer Mosquitto + Z2M (upsert, comme le bloc serial), puis
     msgbox avec les identifiants à saisir dans HA.
  3. Credentials persistés (`.env` ou `mosquitto/credentials` en 600) et
     réaffichables via le menu `status`.
  Mosquitto et Z2M, eux, sont gérés par le kit et migrent automatiquement.
- Cycle de vie sur re-run (stack ayant DÉJÀ un mot de passe) — le wizard doit
  rester idempotent, jamais de changement silencieux d'un secret existant :
  1. Auth active + credentials connus du kit (fichier persisté présent) :
     **ne rien faire, ne rien demander**. Seule action autorisée : re-synchroniser
     la config Z2M si elle a dérivé (même pattern que POSTGRES_PASSWORD).
  2. Auth active mais credentials introuvables (fichier perdu, ou auth
     configurée à la main avant le kit) : irrécupérable (`mosquitto_passwd` ne
     stocke que des hashes) → proposer au choix (a) saisie du mot de passe
     existant, vérifié par un `mosquitto_pub` de test puis persisté, ou
     (b) rotation complète (regénérer, réécrire password_file, upsert Z2M)
     avec le même avertissement HA que la première activation.
  3. Rotation volontaire : entrée dédiée dans le menu `status`
     (« Régénérer le mot de passe MQTT »), à côté du « Redéfinir le mot de
     passe Restic » existant (`install.sh:483`). Toute rotation re-casse la
     connexion HA → toujours explicite + msgbox avec les nouveaux identifiants.

### 1.4 Mot de passe Postgres exposé dans `ps` + injection possible — ✅ TRAITÉ (2026-07-03)
> PGPASSWORD supprimé de backup.sh : le dump passe par le socket local du
> conteneur (auth trust de l'image postgres — validé E2E sur postgres:16 réel).
> Les branches `ui_run`/`bash -lc` (injection possible + de toute façon mortes,
> ui.sh n'étant jamais sourcé par backup.sh) ont été supprimées.
- Où : `scripts/backup.sh:62` (branche `ui_run`) et `:66` (branche console).
- Risques :
  - `docker exec -e PGPASSWORD=…` met le mot de passe en clair dans la liste
    des processus pendant le dump (les deux branches).
  - La branche `ui_run` construit `bash -lc "… PGPASSWORD='${POSTGRES_PASSWORD}' …"` :
    une apostrophe dans le mot de passe casse la commande = injection shell.
- Correction : le dump via le socket local du conteneur ne nécessite aucun mot
  de passe (auth `trust`/`peer` de l'image postgres) :
  `docker exec "$(pg_container_id)" pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" …`.
  Supprimer entièrement PGPASSWORD, et ne jamais interpoler de secret dans une
  chaîne `bash -lc`.

## 2) P0 — Bugs confirmés

### 2.1 `env_get` retourne `KEY=value` au lieu de `value` **[vérifié par exécution]** — ✅ TRAITÉ (2026-07-03)
> Correctif appliqué : awk réécrit (`substr` après trim, plus de `sub()` avec
> `"k"` littéral). Les `strip_key_prefix_if_any` sont **conservés volontairement**
> comme nettoyage défensif des `.env` hérités pollués (`KEY=KEY=value`) — ne pas
> les retirer sans vérifier ce cas. 5 tests bats ajoutés (valeur simple, valeur
> avec `=`, espaces de tête + clé absente, clé préfixe d'une autre, valeur
> héritée polluée). Suite complète 19/19 verte. Corrections annexes du même lot :
> stub whiptail des tests (écrit désormais sur stderr comme le vrai whiptail),
> `STACK_DIR` surchargeable dans `backup.sh`, `is_interactive_tty` fiabilisé
> (cf. §3.8), attentes de tests mises à jour vers le subnet figé 172.30.0.0/24.
- Où : `scripts/lib/env.sh:27`. Dans `sub(/^[[:space:]]*"k"=/, "")`, `"k"` est
  **littéral** à l'intérieur d'une regex `/…/` awk (contrairement au pattern de
  match qui, lui, concatène des chaînes). Le préfixe n'est donc jamais retiré.
- Conséquences :
  - Tout le code compense avec `strip_key_prefix_if_any` saupoudré partout
    (workaround du symptôme, pas de la cause).
  - Endroits SANS workaround → comparaisons cassées :
    - `scripts/install.sh:116-130` : sur ré-installation, les défauts affichés
      (Caddy/UPnP/proxy) ignorent la config existante (`== "0"` / `== "1"` ne
      matchent jamais).
    - Fallbacks latents : `caddy.sh:17-20`, `compose.sh:110-114`,
      `health.sh:26-31`, `zigbee.sh` (`zigbee_mode_get` retomberait sur "none").
      Masqués la plupart du temps parce que `load_env_file` a déjà exporté les
      variables, mais faux dès que le fallback est réellement utilisé.
- Correction : dans l'awk, remplacer le `sub()` par
  `print substr($0, index($0, "=") + 1)` (après trim du leading whitespace),
  puis **supprimer progressivement** les `strip_key_prefix_if_any` devenus inutiles
  (garder la fonction le temps de la transition ; les tests bats doivent couvrir
  `env_get` avec valeur simple, valeur contenant `=`, espaces de tête).

## 3) P1 — Fiabilité (backup en tête)

### 3.1 Échecs de backup silencieux OU cascade d'échecs — ✅ TRAITÉ (2026-07-03)
> backup.sh réécrit : chaque étape (dump, backup/forget par repo) est isolée —
> un repo mort n'empêche pas les suivants, un échec de dump n'empêche pas
> restic — et tous les échecs sont accumulés, loggés en bilan, avec exit 1
> final (systemd voit le run failed). Dump partiel supprimé sur échec
> (pipeline `pg_dump | gzip` + rm). Validé E2E avec restic réel (repo mort en
> premier → rc=1 + repo sain sauvegardé/purgé) et par 3 tests bats.
> Reste ouvert (nice-to-have) : notification active (ntfy/HA) via OnFailure=.
- Où : `scripts/backup.sh:62,97-98` (branche `ui_run` : `|| true` sur pg_dump,
  restic backup, restic forget → le timer systemd rapporte "success" même si tout
  a échoué) ; branche console `:100-104` : `set -e` + trap ERR → **l'échec du
  premier repo (ex. NAS démonté) saute tous les repos suivants**.
- Correction : boucle par repo avec capture d'erreur, continuer sur échec,
  accumuler le statut, `exit 1` à la fin si au moins un échec. Ajouter une
  notification d'échec (persistent notification HA via API, ntfy ou mail).
  Vérifier que la cible est bien montée (`mountpoint -q`) avant `restic backup`.

### 3.2 `ha-backup.service` sans timeout ni durcissement — ✅ TRAITÉ (2026-07-03)

- Correction : `TimeoutStartSec=1h`, envisager `Nice=10`, `IOSchedulingClass=idle`,

### 3.3 `restic forget` sans filtre de tag — ✅ TRAITÉ (2026-07-03)
